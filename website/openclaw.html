What It Does

I built a custom operating-memory layer on top of the OpenClaw personal assistant architecture because my work lives across WhatsApp, Discord, email, browser sessions, repositories, tasks, notes, finance systems, and client documents. The point is to let the assistant carry context across those surfaces: capture raw evidence, turn it into validated facts, search the knowledge base, respect chat-level access boundaries, and act through the right tool without losing the thread.

There are two useful measures of a system like this. First: can it be called into real work, carry shared context forward, and recover when corrected? Second: can it retrieve the right information that I can't remember?

How Facts Work

A fact is a structured claim extracted from raw material: typed, sourced to message IDs, dated, scoped to a chat, with visibility and validation status. Examples: a project constraint, a decision, a correction, a preference, an investment rule, a relationship, an idea.

26,627 candidate facts were extracted. 13,035 were accepted, meaning allowed to affect future context. The rest are rejected, superseded, or stale. This filtering matters because chat is noisy. People joke, change their minds, correct themselves, and speak differently in different rooms.

Architecture

Postgres: Source of Truth

Postgres stores the raw messages, media references, extracted candidate facts, accepted facts, validation status, provenance, chat scope, access rules, task records, and structured ledgers. The same store is searchable through vector retrieval, so the system can find relevant history without treating search results as truth by themselves. If I need to know exactly what was said, where a fact came from, whether it is accepted, or whether it can cross rooms, Postgres is the authority.

Obsidian: The Readable Knowledge Model

Accepted facts in Postgres are distilled into person pages, chat pages, project notes, idea notes, entity pages, and architecture notes. This is where the system becomes legible to a human: not just rows in a database, but a wiki of people, projects, constraints, history, and decisions.

QMD: The Search Layer

QMD indexes Obsidian and project documents for hybrid keyword and semantic search. It helps find relevant material quickly. It does not create truth and it does not replace Postgres. It is a retrieval layer, not the authority layer.

At runtime the agent combines them: Postgres for exact source and permissioned facts, Obsidian/QMD for broader context and project memory, then an access-control check before anything is injected into the current chat. After work is done, new outcomes can be captured back into Postgres and later distilled into the wiki.

Data Flow

Capture raw evidence → Extract candidate facts → Validate → Build knowledge layer from accepted facts → Retrieve relevant context → Check access control (who, which channel, what scope) → Inject only what's allowed → Execute through the right tool → Capture outcomes back to Postgres → Distill into wiki

Access Control Is Structural

Access control is not bolted on. The system checks who is asking, which channel they are in, which chat the fact came from, what access scope applies, and whether the fact can cross rooms. Attribute-based access control (ABAC), enforced in Postgres at the query level. This is what makes shared memory useful without making it a leak.

Most chats are chat-scoped: they see only their own messages and global facts. A few Discord channels and Stefan's DM are full-scoped: cross-chat access to everything. Some Discord guild channels are guild-scoped: they see other channels in the same Discord server, nothing wider. The boundary is structural, not advisory. You cannot prompt your way past it.

What It Has Done

Financial Portfolio

Collating a personal balance sheet across four share broker accounts, crypto wallets, property, loans, cash, email attachments, FX, lots, cost basis, and current holdings. Not just listing assets but answering what is owned, where it came from, what changed, and what evidence supports the number. Dividend tracking, cost basis calculations, and monthly reconciliations against broker statements.

DuneCity

Working inside a C++/SDL2 Dune Legacy fork integrating Micropolis-style city simulation into a Dune II-style RTS. The system keeps project constraints live: zones stay 2x2, slabs replace roads and power lines, WindTraps power the city layer, save/load determinism matters. Release builds, versioning, CI/CD, installer packaging, and the website you're reading this on.

Collaboration

Turning chat-based work with collaborators into strategy packs, website recommendations, product positioning, GTM notes, and client-ready material. Source conversations, decisions, objections, and final output stay connected through the system. 344 people profiled, 79 with structured facts the system can reason about.

Email Triage

80,462 emails archived and searchable. Gmail triage under GTD rules: inbox items become decisions, archive, waiting-for, or next actions. Actionable emails convert to Todoist tasks. The email archive runs on a local SQLite database with vector embeddings, so semantic search works without hitting Gmail's API.

Infrastructure

WhatsApp and Discord capture pipelines, Messenger bridge work, Gmail triage into Todoist, agent job queue with Postgres-backed retry and stall detection, project reconciliation, browser publishing, and content drafting. 157 agent jobs dispatched, 139 completed successfully. The system delegates implementation work to Claude Code through a durable job queue.

The Correction Loop

481 corrections logged. Each correction is a structured fact: what was wrong, who corrected it, when, and in which chat. Corrections feed back into the system as constraints. A correction about confusing two people becomes a disambiguation rule. A correction about a wrong portfolio number becomes a ledger validation gate. A correction about a fabricated quote becomes a hard rule against invention.

The system's core failure mode is what I call "competence theatre": clean narration before source checks, "done" when only planned, stale-memory confidence, plausible tool paths, and freehand math. The correction loop is how trust gets rebuilt. Not by promising to do better, but by writing a rule, a gate, or a spec that makes the same failure structurally harder.

Key Principles

  • Verify before claiming. Check canonical sources before claiming data exists, is available, or is unavailable. Don't infer finance state from memory. Read the ledger.
  • No invention. Never fabricate a name, quote, message, event, or citation to make an answer feel complete. "Plausible" is not "true."
  • Search the person, not the keyword. For "what did X recommend about Y," lead with X's actual stack and affinities, not a brand-name keyword hunt.
  • Status words are exact. Planned, queued, built, tested, sent, deployed are different. No "done" without the concrete artifact.
  • Consent is not capability. Third-party requests touching my assets need my consent. Capability is not authorisation.
