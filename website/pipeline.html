Behind the game

How Dune City is built and tested

Dune City is developed on one Mac mini, tested in GitHub Actions and on two on-demand AWS machines, and released from a pre-qualified, tagged commit. AI coding agents share a single staging checkout and a single build. A home-grown scheduler, dunecity-queue, fans test games and test suites out to the AWS workers and switches them off when the work is done.

As of 22 November 2026. The current stable release is 1.0.875, published 21 November 2026.

Development workflow

All work lands in one checkout and one build, so every agent tests the same binary.

  1. Edit. Coding agents (Claude Code, Codex and OMP) work in the staging checkout on branch integrate/feature-batch. Each claims the files it will touch, so two agents never edit the same file.
  2. Build. There is one build tree: CMake and Ninja, C++17, libraries from Homebrew, compiler output cached by ccache. A shared lock allows only one build, local test run or Git change at a time.
  3. Switch. Any change to AI or game behaviour goes behind an on/off config switch. Tests then compare OFF and ON in the same binary instead of building one tree per idea.
  4. Commit and test. Tests run against a committed, full SHA, never the working tree. Headless tests go to the AWS queue; only the Mini-only tests run locally.
  5. Integrate. One integrator combines accepted changes and pushes the batch to GitHub, which starts CI.

The stack is a C++17 and SDL2 game engine, Python for test harnesses and packaging, Emscripten for the browser build, and Node and PHP for the multiplayer services. CI builds get their libraries from vcpkg rather than Homebrew.

Three tiers decide how much runs. integration (56 tests) is the quick gate on every change. nightly (all 242) is the broad regression run and collects every result rather than stopping at the first failure. release-smoke checks the actual packaged app before a release.

AWS test queue

Accepted is not passed: the result comes from dunecity-queue report JOB --follow.

Two commands cover most use. dunecity-queue ctest --rev SHA --machines aws aws-mel2 -L integration runs registered tests, and dunecity-queue submit --rev SHA -- python3 tests/ai/vanilla-match.py ... plays a batch of AI games.

Release path

A release is a commit that has already passed qualification, tagged and then published channel by channel.

  1. CI. Every push to integrate/feature-batch runs the Build Dune Legacy workflow: tests on Linux, plus Windows, macOS, Linux and browser builds.
  2. Staging packages. A green batch becomes an immutable staging pre-release on GitHub (two-hour debounce, daily safety net). Staging builds carry a dev version label, never become Latest, and their browser copy goes to /play-staging, separate from the stable /play.
  3. Qualification. Green CI also triggers Qualify release candidate: the broad nightly headless suite, once per frozen commit, on the Mini with a GitHub-hosted Mac as fallback. On the Mini it sends its test games to AWS.
  4. Tag. Pushing vX.Y.Z builds the official packages. The Mini signs and notarises the Mac build and signs the update feeds.
  5. Publish. The release job publishes to GitHub; SourceForge and the browser build follow automatically. A channel counts as done only after its live destination is checked.
